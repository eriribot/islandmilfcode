# DeepSeek 模式工作流

本文档描述未来用户手动开启 DeepSeek 模式后的推荐工作流。首版仅作为实现蓝图，不包含代码。

## 总体原则

DeepSeek 模式默认关闭，由用户在设置页手动开启。

开启后，系统不改变剧情事实、不重写世界书、不替换角色卡。它只改变以下内容：

- 上下文打包策略。
- 记忆注入预算建议。
- DS 友好标题和标签。
- 证据包格式。
- 输出格式护栏。
- 联网检索门控方式。

联网检索采用“每轮先自检、命中才触发”的策略，而不是全局常驻搜索。
自检重点优先放在外貌、服装、发型、饰品、角色设计小细节和 canon 细节上；情绪承接和普通关系推进不应触发联网。

## 生成链路

推荐链路：

```text
用户输入
  ↓
DeepSeek 初登场 bootstrap 自检
  ↓
候选身份/外貌短索引进入 scenePresence 副任务
  ↓
副 API: scenePresence 判定
  ↓
同步当前事件、地点、时间和 active target
  ↓
DeepSeek 适配层打包上下文
  ↓
主 API: DS V4-Pro 生成正文
  ↓
副 API: progress / phone / summary / memoryDB 更新
```

主模型仍然负责正文。副 API 仍然负责后台结构化任务。DeepSeek 模式只是夹在 prompt 构建前的一层上下文整理。

## 上下文打包顺序

未来实现时，DeepSeek 模式建议按以下顺序组织 prompt：

1. 全局稳定前缀：输出标签、DeepSeek 模式规则、同层卡总原则、工具约定。
2. 会话稳定前缀：角色 id/别名 catalog、bootstrap catalog、稳定外貌锚点 catalog。
3. 本轮动态上下文：当前事件、地点、时间、scenePresence、证据包、memoryDB 检索结果。
4. 热镜头层：在场角色完整 0 层卡、关系指导、外貌锚点、声线样例。
5. 温索引层：非在场角色 1-3 行后台胶囊。
6. 最近对话和玩家当前输入。
7. 输出任务尾部：本轮具体生成要求、禁止事项和停止位置。

注意：长期背景层只能补缺，不能抢走当前镜头焦点。
注意：为了 DeepSeek context cache 命中，当前时间、地点、scenePresence、玩家输入和工具结果都不能插到稳定前缀之前。

## 主副 API 分工

### 主 API

推荐模型：DeepSeek V4-Pro。

职责：

- 生成可见正文。
- 遵守当前镜头和输出格式。
- 使用热镜头层完成角色台词、动作、心理和叙事节奏。
- 在需要时引用证据包，但不展开检索过程。

不负责：

- 写入变量。
- 更新 memoryDB。
- 生成摘要。
- 判断手机消息。
- 联网检索。

### 副 API

可使用 DeepSeek V4-Flash、DeepSeek V4-Pro 或其他稳定 OpenAI 兼容模型。

职责：

- `scenePresence`：判断明确在场、转场目标、不在场和不确定角色。
- `progress`：抽取变量变化、事件推进、时间地点变化。
- `summary`：压缩历史，不回写权威变量。
- `phone`：识别手机发送意图和手机后台回复。
- 未来可选：证据包蒸馏、搜索查询规划、同人事实置信度审计。

## 角色保留策略

DeepSeek 模式不放弃任何角色，但也不让所有角色常驻完整卡。

规则：

- 当前在场角色：完整 0 层卡 + 关系指导 + 声线样例。
- 转场目标：完整 0 层卡或高密度证据包。
- 非在场角色：后台胶囊，不即时反应。
- 长期未出场角色：保留最近状态、未回收伏笔、自然入场条件。

后台胶囊示例：

```text
[CHAR:michiru][后台胶囊]
最近状态：乐团线与社团音乐线已接上，仍重视音乐人的自主选择。
未回收伏笔：如何平衡 icy tail 与 blessing software 的作曲时间。
入场条件：音乐、Live House、作曲委托、亲族关系或社团制作压力被当前场景明确触发。
禁止：未被联系或未在场时不得突然插话。
```

## 记忆和预算建议

DeepSeek 模式可以利用更长上下文，但预算仍要按权重分配：

- 热镜头层优先级最高。
- 当前剧情事件优先于全局摘要。
- route delta 优先于原作惯性。
- 结构化事实优先于长散文。
- 最近原文保留 5-8 条，避免摘要替代现场语气。
- memoryDB 注入可以比普通模式更宽，但必须按当前角色、事件、地点和用户输入过滤。

建议不要把 token budget 单纯拉满。更好的做法是让每一块都可命中、可解释、可审计。

## 格式护栏

DeepSeek V4 容易在长聊后漏标签或多输出解释。开启 DeepSeek 模式后，未来实现应额外强化：

- 可见正文必须包在既有可见标签中。
- 快捷回复选项必须完整闭合。
- 输出到停止标签后立即结束。
- 禁止输出审计过程、检索过程、系统解释。
- few-shot 示例只放格式，不放会污染剧情的长例文。

这部分与 `DeepSeek_V4_格式优化指南.md` 配合使用。

## 联网检索预留

首版不实现联网检索。后续如果加入 sidecar，建议只在以下情况触发：

- 用户明确询问原作、同人资料、外貌、卷数或剧情事实。
- 本地同人数据库置信度不足。
- 当前剧情需要核对 canon，不核对会明显写错。

检索结果必须先蒸馏为证据包，再进入主 prompt。不要把网页、论坛帖或百科原文直接塞给主模型。

### 每轮自检门控

每次生成前都先做一次轻量自检，判断这轮是否值得联网。

推荐自检问题：

- 当前用户输入是否要求核对原作、外貌、卷数、设定或时间线事实？
- 当前轮是否需要描写发色、眼睛、发型、服装、饰品、手机头像、社团/品牌/作品名等设计小细节？
- 当前轮本地同人数据库的置信度是否不足以安全写作？
- 如果不联网，这轮是否很可能写错 canon、把角色写偏或把关键事实归因错位？
- 是否存在必须补证据的新增角色、剧情卷或外部资料？
- 当前轮是否存在初登场、首次正面描写、陌生人识别、外貌描述识别或事件即将拉入新角色？
- bootstrap 候选是否指向 `CHAR:izumi`、`CHAR:sonoko`、`CHAR:akane` 等容易在初登场写偏的角色？

门控结果只有两种：

- `need_search = false`：直接走本地证据包和已有上下文。
- `need_search = true`：触发搜索 / 抓取 / 蒸馏流程，再把结果写回证据包。

初登场外貌类自检优先查本地 bootstrap 锚点。只有本地头像、角色卡、世界书和已确认记忆都不足时，才把外貌问题升级为联网检索。

未来 sidecar 流程：

```text
触发检索
  ↓
查询规划
  ↓
搜索 / 抓取
  ↓
来源去重和可信度排序
  ↓
事实蒸馏
  ↓
写入临时证据包或同人数据库缓存
  ↓
主模型只读取证据包
```

## 验收标准

未来代码实现 DeepSeek 模式时，至少满足：

- 用户可以手动开启/关闭，默认关闭。
- 关闭时现有生成行为不变。
- 开启时不修改世界书原文和角色核心提示。
- 非在场角色不会因后台胶囊产生即时反应。
- 当前在场角色仍能拿到完整 0 层卡。
- DS 友好证据包包含角色 ID、来源、置信度、适用条件和禁止推论。
- 主 API 只写正文，副 API 继续处理后台结构化任务。
