# 第七卷自由输入玩法与路线开关方案

状态：方案文档，当前轮不做代码实现。

目标：在不破坏现有事件链、关系轴、记忆库和自由正文输入框架的前提下，让第七卷后续路线可以有“玩法感”，并让 AI 只需要判断 `yes/no` 就能写入稳定剧情开关，而不是靠正文里一句“好像说服了”来模糊确认。

## 当前约束

1. 第七卷事件链保持线性：`SAE_07-1 -> SAE_07-2 -> SAE_07-3 -> SAE_07-4 -> SAE_07-5 -> SAE_07-6 -> SAE_07-7 -> SAE_07-8`。分支不能通过乱跳事件来做。
2. `SAE_07-7` 是 2013-03-01 周五 User 请惠回到共同企划/副代表位置；`SAE_07-8` 是 2013-03-04 三月吉日毕业典礼节点，并回收 2013-03-01 美术准备室誓约。
3. 留下路线是英梨梨、诗羽继续留在 blessing software。它不是“创作者路线”的同义词。
4. 红坂朱音线是攻略朱音本人。朱音不是纯反派，击退朱音只表示阻止她带走黑金二人组，不表示删除朱音或否定她的创作魅力。
5. 单飞/其他路线是 User 自己或其他走向，不等于黑金二人组失去主体性。
6. `relationship.ts` 已有 `affinity` 和五人专属 `obsession`，红坂朱音没有执念轴。不要为了朱音线硬加“对伦也执念”。
7. `StatusData.world` 当前只承载时间、地点、当前主线、近期事件、主线事件状态。不要把大量路线开关塞进固定 world 字段。
8. `runtimeFlags` 更像 UI/运行时辅助，不适合作为剧情权威。
9. `memoryDB.attributes` 已支持任意 key，且每个 `(targetId, key)` 只有一个活跃快照，适合做轻量路线开关。

## 架构证据

- `剧情第七卷.json` 已经提供事件卡、触发日期、前置事件、可接续事件、分支控制参考和 User 介入参考，适合作为剧情主干。
- `message-format.ts` 当前 `<state_delta>` / `<progress>` 解析时间、地点、主线事件、好感、执念、五维、物品、身体计数等字段；尚未解析 `剧情开关.*:yes/no`。
- `actions/index.ts` 会通过剧情库白名单与 `plot-routing.ts` 限制主线事件 ID，说明“路线判断”应该走现有白名单/路由层，而不是让 AI 自造事件。
- `memorydatabase/types.ts` 的 `MemoryAttributeRow` 明确允许任意属性 key，适合存 `plotFlag.*`。
- `HAREM_ROUTE_DESIGN.md` 已有先例：复杂关系不做 O(N^2) 矩阵，用单边属性和事件痕迹解决。

## 迭代记录

### 第 1 轮：只靠事件卡分支

设想：在 JSON 里继续追加更多数字事件，例如 `SAE_07-9/10/11`，用 `前置事件` 和 `可接续事件` 表达留下、朱音、单飞。

问题：自由输入下，玩家可能在 07-5 前就调查朱音，也可能在 07-7 后先找惠、英梨梨、诗羽或朱音。只靠事件卡会迫使剧情分支变成“跳节点”，容易破坏当前白名单和时间闸。

结论：事件卡只做时间主干和关键场面，路线分支不要直接拆进大量事件 ID。第七卷主干继续线性。

### 第 2 轮：做数值资源小游戏

设想：引入行动点、制作力、灵感、防线值、朱音压迫值等资源。玩家每次自由输入都消耗资源，像经营小游戏一样推进。

问题：好玩，但会把当前项目从“自由正文 + 轻量状态”推向“显式数值游戏”。这需要 UI、回合制时间、行动结算和失败反馈，当前架构没有准备好，且容易让正文变成刷数值。

结论：不要先做大资源系统。保留“小游戏感”，但把它压缩成少量 yes/no 检查点。

### 第 3 轮：扩展关系轴

设想：给英梨梨、诗羽、惠、朱音增加更多轴，比如创作信任、社团信任、朱音压力、去留倾向。

问题：`relationship.ts` 现在的主轴是对 User 好感与五人对伦也旧线执念。把路线条件塞进角色关系轴，会让“英梨梨留下”被误判成“英梨梨更喜欢 User”，也会让红坂朱音被错误拉进执念系统。

结论：路线开关不属于普通关系轴。角色关系继续用 `affinity/obsession`，路线事实另存。

### 第 4 轮：用 worldState 或 runtimeFlags 存路线

设想：在 `worldState` 或 `runtimeFlags` 里直接写 `akaneRepulsed=true`、`stayRoute=true`。

问题：`StatusData.world` 是当前世界游标，不是路线仓库；`runtimeFlags` 适合 UI 和临时状态，不适合剧情权威。直接塞字段会造成保存、摘要、检索、路由判断之间职责不清。

结论：不放 `StatusData.world`，不以 `runtimeFlags` 为权威。路线开关放 `memoryDB.attributes`，需要注入 prompt 时再读出。

### 第 5 轮：布尔剧情开关层

设想：新增一种可解析字段：

```text
剧情开关.v07.blackgold_counterwill:yes
剧情开关.v07.akane_route_open:no
```

AI 只判断本轮正文是否明确满足某个开关条件。满足写 `yes`，明确破坏写 `no`，不确定就省略。写入时存为：

- `targetId`: `route:v07`
- `key`: `plotFlag.v07.blackgold_counterwill`
- `value`: `yes` 或 `no`
- `valueType`: `boolean` 或 `string`

优点：不用建新表，不破坏事件链，不让 AI 自造路线 ID，也能被 `plot-routing.ts` 后续读取。

结论：这是 V1 最合适的核心方案。

### 第 6 轮：把玩法做成“场景检查点”

设想：小游戏不是 UI 先行，而是嵌入正文场景。玩家自由输入仍是自然语言，AI 负责把自然语言动作映射成 yes/no 开关。

例子：

- 企划拼装：玩家是否明确提出核心女主、制作范围、成员职责、失败预案。
- 朱音攻防：玩家是否识别朱音不是纯恶役、是否给出能与大厂战场对抗的创作理由、是否尊重黑金二人组选择。
- 情报调查：玩家是否从伊织、町田、诗羽、英梨梨处得到朱音压力信息。
- 惠共同企划：玩家是否把惠从“女主角原型”提升为共同企划/副代表。

结论：玩法不靠按钮堆，而靠“自由输入 -> 场景结果 -> yes/no 开关”的稳定落库。

## 最终方案

采用“线性事件链 + 路线开关层 + 场景检查点”的三层结构。

### 第一层：线性事件链

第七卷事件照常按主线日期推进。事件卡负责：

- 时间锚
- 场景参考
- 人物状态
- 关键情节
- User 介入边界

事件卡不负责直接结算路线。比如 `SAE_07-8` 只把“黑金共同击退朱音意志”点亮为必要条件，不直接判定黑金二人组已经留下。

### 第二层：路线开关

建议 V1 开关如下：

| key | yes 含义 | no 含义 |
|---|---|---|
| `plotFlag.v07.akane_pressure_seen` | User 已知道朱音压力存在 | User 仍不知道朱音压力 |
| `plotFlag.v07.akane_formal_offer_seen` | 御影亭/商业挖角已被显性得知或后台确认 | 正式挖角未进入路线判断 |
| `plotFlag.v07.blackgold_shaken` | 英梨梨、诗羽被朱音战场动摇 | 尚未动摇 |
| `plotFlag.v07.blackgold_counterwill` | 黑金共同击退朱音意志成立 | 未成立或被破坏 |
| `plotFlag.v07.user_knows_counterwill` | User 已通过转述/画稿/会议得知黑金誓约 | User 尚不知道 |
| `plotFlag.v07.megumi_coplanner` | 惠已被请回共同企划/副代表位置 | 惠仍只是被动女主角或旁观者 |
| `plotFlag.v07.second_project_seed_ready` | 第二作企划初稿足以成为行动基础 | 仍只是空口热血 |
| `plotFlag.v07.eriri_high_battlefield_supported` | User 给英梨梨提供能燃烧的高强度创作理由 | User 只是在保护/挽留 |
| `plotFlag.v07.utaha_author_pride_supported` | User 承认诗羽作为霞诗子的才能与不死心 | 诗羽仍被当作附属或工具 |
| `plotFlag.v07.akane_route_open` | 朱音本人攻略入口打开 | 朱音只作为压力源存在 |
| `plotFlag.v07.akane_repulsed` | 已成功阻止朱音带走黑金二人组 | 尚未击退 |
| `plotFlag.v07.stay_route_viable` | 留下路线具备可执行条件 | 留下路线条件不足 |
| `plotFlag.v07.solo_route_open` | User 单飞/其他路线具备入口 | 未进入单飞/其他 |

### 第三层：场景检查点

每个检查点都由自由正文触发，但落库只写 yes/no。

1. 企划拼装检查点
   - `second_project_seed_ready:yes`
   - 条件：玩家提出的不只是“再做游戏”，而是有主题、女主核心、成员职责、制作范围。

2. 惠共同承担检查点
   - `megumi_coplanner:yes`
   - 条件：玩家明确让惠拥有纠正、争吵、制衡代表的权力，而不是只让她当素材。

3. 黑金誓约检查点
   - `blackgold_counterwill:yes`
   - 条件：07-8 回收三天前美术准备室誓约，或后续由英梨梨/诗羽转述确认。

4. 朱音攻防检查点
   - `akane_repulsed:yes`
   - 条件：玩家不是禁止接触朱音，而是提供足以让英梨梨和诗羽“不需要被朱音带走也能燃烧”的方案。

5. 朱音攻略检查点
   - `akane_route_open:yes`
   - 条件：玩家承认朱音的创作强度、危险性和自毁性，并与她建立非敌我扁平化的对话。

## 路线判定表

| 路线 | 必要 yes | 常见阻断 |
|---|---|---|
| 留下路线 | `megumi_coplanner`、`second_project_seed_ready`、`blackgold_counterwill`、`eriri_high_battlefield_supported`、`utaha_author_pride_supported`、`stay_route_viable` | 只说“别走”、只保护英梨梨、不承认诗羽创作者自尊、不让惠参与决策 |
| 击退朱音 | `akane_formal_offer_seen`、`blackgold_shaken`、`blackgold_counterwill`、`akane_repulsed` | 把朱音写成纯恶役、禁止黑金接触高强度创作、没有替代战场 |
| 红坂朱音线 | `akane_pressure_seen`、`akane_route_open`，后续再加朱音好感/信任条件 | 把朱音只当反派打掉，或完全否定她的创作魅力 |
| 单飞/其他 | `solo_route_open`，且 `stay_route_viable` 不强制为 yes | 世界只围绕 User 转，导致黑金二人组失去独立创作者同盟 |

注意：`blackgold_counterwill:yes` 可以同时服务留下路线和朱音线。它不是“朱音线关闭”，而是表示朱音必须面对两位创作者已经有自己的反击意志。

## 自由输入如何映射

| 玩家自由输入行为 | 建议开关 |
|---|---|
| 调查伊织、町田、诗羽，确认朱音商业邀约 | `akane_pressure_seen:yes` |
| 得知御影亭饭局或《寰域编年纪》正式邀约 | `akane_formal_offer_seen:yes` |
| 在 07-7 中把惠请回共同企划/副代表 | `megumi_coplanner:yes` |
| 写出第二作企划书并能说明制作范围 | `second_project_seed_ready:yes` |
| 通过画稿、诗羽转述、英梨梨态度变化得知美术准备室誓约 | `user_knows_counterwill:yes` |
| 给英梨梨的是高强度创作战场，不是单纯保护 | `eriri_high_battlefield_supported:yes` |
| 明确承认诗羽不只是刺激英梨梨的工具 | `utaha_author_pride_supported:yes` |
| 与朱音对话时承认她的准确和危险，而不是扁平反派化 | `akane_route_open:yes` |
| 只说“不准去朱音那里”“别离开社团” | 不写 `stay_route_viable:yes`，严重时写 `stay_route_viable:no` |

## 推荐输出格式

未来实现后，AI 在 `<state_delta>` 中只输出变化字段：

```text
<state_delta>
剧情开关.v07.megumi_coplanner:yes
剧情开关.v07.second_project_seed_ready:yes
剧情开关.v07.blackgold_counterwill:yes
</state_delta>
```

明确破坏时：

```text
<state_delta>
剧情开关.v07.stay_route_viable:no
</state_delta>
```

不确定时不输出。禁止写“可能 yes”“大概成立”“玩家已经说服”这种自然语言确认。

## 后续实现任务

1. `message-format.ts`
   - 给 `ProgressUpdate` 增加 `plotFlags: Array<{ key: string; value: 'yes' | 'no' }>`。
   - 在 `buildStateDeltaInstruction` / `buildProgressInstruction` 加 `剧情开关.<key>:yes/no` 说明。
   - 在 `parseStateBody` 中解析 `剧情开关.v07.xxx:yes|no`。

2. `memorydatabase/commit-points.ts`
   - 把 plotFlags 写入 `attributes`。
   - 推荐 `targetId='route:v07'`，`key='plotFlag.v07.xxx'`，`value='yes'|'no'`。

3. prompt 注入
   - 在构建当前剧情上下文时读出 `route:v07` 下的 plotFlag，并注入“当前路线开关”。
   - 只注入当前卷相关开关，不把全库开关全塞进 prompt。

4. `plot-routing.ts`
   - 第七卷后续真正分支时，读取 plotFlag 做路由判断。
   - 不要让 AI 输出未来事件 ID 来决定路线。

5. UI/调试
   - V1 可以只在记忆库 attributes 面板可见。
   - V2 再做手机状态页或路线调试页，显示 yes/no 开关。

6. 玩法验证
   - 如果未来真的做可视化小游戏或 UI 交互，按 `develop-web-game` 要求提供 `window.render_game_to_text` 和 `window.advanceTime(ms)`。
   - 每次玩法变更后用 Playwright 检查按钮、状态、截图、文本状态和控制台错误。
   - 目前没有做 UI 小游戏，所以本轮不跑 Playwright。

## V1 结论

能做到，而且最稳的做法不是让 AI 写长段文字确认路线，而是让 AI 在自由正文之后输出少量布尔开关。

V1 只需要三件事：

1. 保持第七卷事件链线性。
2. 增加 `剧情开关.*:yes/no` 的解析与落库。
3. 把第七卷玩法拆成企划、惠共同承担、黑金誓约、朱音攻防、朱音攻略五类场景检查点。

这样玩家仍然可以自由输入，剧情仍然像小说推进，但路线结算有稳定机器可读状态，不靠“文字感觉说服了”。
