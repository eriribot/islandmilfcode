# V07 游戏开发难度与酒馆同层仿真交接 v0.1

> 接手对象：5.6 sol
>
> 文档性质：产品规则、手工仿真协议和下一轮开发计划。
>
> 当前状态：只写 Markdown，不改 TypeScript、HTML、CSS、prompt、memoryDB 或宿主接通链。
>
> 目标路线：`solo` 单飞线、`akane` 红坂朱音线。

## 0. 先看结论

本版本先采用一个“中等偏难、开罗式轻经营”的开发模拟，不追求复杂数值，也不让 AI 自由发明经营规则。

核心节奏固定为：

```text
路线事实判断
    -> 玩家手动确认单飞线或朱音线
    -> 没有项目时才执行一次“定企划”
    -> 项目名确认后进入开发模式
    -> 每周安排 5 个工作日开发 + 1 个周末休整/约会
    -> 六个行动全部填满后，才提交这一周的正文
    -> AI 按冻结的周计划写正文
    -> 手工按固定表结算，不允许 AI 自己改分数
```

“酒馆同层仿真”指：路线判断、周计划、正文和本周结算都在同一个酒馆聊天层里用 Markdown 展示；不创建隐藏楼层，不写代码，不调用数据库，也不另造一个游戏页面。

## 1. 不可违反的产品规则

### 1.1 项目生命周期

项目只有两个状态：

```text
NO_PROJECT
  -> CONCEPT
  -> PROJECT_CREATED
  -> WEEKLY_DEVELOPMENT
```

规则：

- `NO_PROJECT` 时，玩家可以执行一次 `concept`，填写项目名、类型、平台和一句话卖点。
- 项目名确认后，项目进入 `PROJECT_CREATED`。
- `PROJECT_CREATED` 之后，`concept` 永久从每周行动池移除。
- “定企划”不是每周行动，不消耗每周 slot，也不应在已经有项目时反复出现。
- 如果项目名需要修改，应该是明确的“项目重开/版本重命名”操作，不能伪装成普通开发行动。

### 1.2 路线判断和开发模式分离

- 先判断路线，再决定是否激活对应的开发 session。
- 事实不足时，显示“未满足”，不能因为玩家口头说想走某线就直接激活。
- 路线 choice 由玩家手动确认，一次锁定；AI 不得替玩家选路线。
- 路线 choice 只决定路线 profile，不直接增加项目分数。
- 没有合法路线 session 时，不能进入周计划提交。

### 1.3 每周六个行动位

每周固定六个 slot：

| Slot | 类型 | 规则 |
| --- | --- | --- |
| 周一 | 工作日开发 | 从开发行动池选一个 |
| 周二 | 工作日开发 | 从开发行动池选一个 |
| 周三 | 工作日开发 | 从开发行动池选一个 |
| 周四 | 工作日开发 | 从开发行动池选一个 |
| 周五 | 工作日开发 | 从开发行动池选一个 |
| 周末 | 休整/约会 | 只能选 `rest_date` 语义 |

- 周一至周五允许重复同一开发类型，但重复会产生疲劳或边际收益下降。
- 周末不能改成普通开发；如果玩家不想约会，可以选择独处休整。
- 六个 slot 没有全部填写时，正文提交按钮必须视为不可用。
- 玩家可以在提交前改选行动、目标和自然语言意图。
- 点击“提交本周正文”后，六个 slot 一起冻结。

### 1.4 AI 的权限

AI 只负责把冻结的周计划写成故事：

- 可以写工作过程、冲突、临时困难、人物互动和周末场景。
- 可以把玩家意图演绎成不同的叙事结果。
- 不可以替换某一天的行动类型。
- 不可以凭正文自行增加、减少或重算项目分数。
- 不可以自动打开路线、项目或 session。
- 不可以把没有选择的角色写成已确认的合作对象。

## 2. 推荐开发难度

### 2.1 总体定位

推荐难度：`标准 / 中等偏难`。

目标体验不是“每周都可能暴毙”，而是让玩家持续做取舍：

- 只堆进度，会积累疲劳和 Bug。
- 只休息，会错过项目窗口。
- 只照顾某个人，会牺牲其他轨道。
- 单飞线资源更紧，朱音线压力更高。
- 一周计划本身是主要决策，不再额外叠加复杂员工技能树。

### 2.2 第一版只保留五个积分

为方便酒馆手工仿真，第一版只维护以下五个数字：

| 字段 | 范围 | 含义 |
| --- | ---: | --- |
| `progress` 完成度 | 0–100 | 项目离可交付还有多远 |
| `quality` 质量 | 0–100 | 剧本、美术、音乐、程序和打磨的综合质量 |
| `fatigue` 疲劳 | 0–10 | 团队当前负担，越高越危险 |
| `budget` 预算 | 0–20 | 还能承受多少资源消耗 |
| `bond` 关系余量 | 0–10 | 只表示本周互动带来的关系空间，不等价于好感度 |

建议项目创建后的初始值：

```text
progress = 8
quality  = 8
fatigue  = 0
budget   = 16
bond     = 0
```

这些是仿真建议，不是生产数值契约。接手时可以调整，但要保持整数和可手算。

### 2.3 工作日基础行动表

工作日从以下行动池选择。行动名称可以在正文中换成自然语言，但结算 ID 不变。

| action ID | 显示名 | progress | quality | fatigue | budget | 适合叙事 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| `scenario` | 剧本 | +2 | +2 | +2 | -1 | 改稿、争论、人物动机 |
| `art` | 原画 | +2 | +2 | +2 | -1 | 立绘、CG、风格冲突 |
| `music` | 音乐 | +1 | +2 | +1 | -1 | 作曲、选曲、录音 |
| `programming` | 程序 | +3 | +1 | +3 | -2 | 引擎、演出、Bug |
| `polish` | 打磨/测试 | +1 | +3 | +1 | -1 | 试玩、修正、统一体验 |

同一周同一 action 连续使用两次时，第二次按以下规则处理：

- `progress` 和 `quality` 各少 1。
- `fatigue` 额外加 1。
- 正文中必须出现“重复劳动、瓶颈或争执”的一种表现。

### 2.4 周末 `rest_date` 表

周末必须从下面三种语义中选一种：

| 目标 | fatigue | budget | bond | 叙事范围 |
| --- | ---: | ---: | ---: | --- |
| 独处整理 | -3 | 0 | 0 | 整理资料、睡眠、重新排期 |
| 合法角色休整 | -2 | -1 | +1 | 吃饭、散步、谈创作，不自动恋爱升级 |
| 高压关系会面 | -1 | -1 | +2 | 只在路线与在场条件允许时使用 |

`rest_date` 不是免费刷关系：如果疲劳已经是 0，剩余恢复量丢失；如果目标不合法，必须退回重新选择。

### 2.5 路线难度修正

#### 单飞线 `solo`

推荐难度：资源 `3/5`，时间 `2/5`，关系 `3/5`。

- 每周固定额外 `budget -1`，表现为外包、借设备或临时资源不足。
- 选择合法合作对象时，某个工作日可获得 `quality +1`，但该日 `fatigue +1`。
- 不允许默认把英梨梨、诗羽、惠写成固定员工。
- 黑金二人组必须保留不依赖 User 的创作者同盟。
- 如果五个工作日全部独自完成，本周 `quality -1`，但 `bond` 不受影响。

#### 红坂朱音线 `akane`

推荐难度：资源 `2/5`，时间 `4/5`，关系压力 `5/5`。

- 每周 `fatigue +2`，表现为朱音的截止期、修改和高压 brief。
- `scenario` 或 `art` 与朱音路线场景契合时，可获得 `quality +1`，但再加 `fatigue +1`。
- 周末与朱音会面时，`bond +2`，同时 `fatigue +1`；不能无代价获得关系收益。
- 英梨梨、诗羽不是默认员工；黑金共同反击仍然是路线的重要阻力。
- 朱音不能替玩家自动决定五个工作日的安排。

### 2.6 每周评价和软失败

第一版不设置立即 Game Over，采用软失败：

| 评价 | 条件 |
| --- | --- |
| S | 本周 `progress >= 12`、`quality >= 12`、`fatigue <= 4` |
| A | 本周 `progress >= 9` 且 `quality >= 9` |
| B | 本周 `progress >= 6` |
| C | 低于以上条件，或出现严重资源问题 |

硬约束：

- `budget <= 0` 时，下一周不能使用需要预算的行动，只能独自完成或休整，直到获得事件资源。
- `fatigue >= 8` 时，所有工作日行动都要在正文中表现明显代价；不能继续写成无损高效。
- `progress >= 100` 时项目进入“完成候选”，不自动宣告商业成功。
- `quality`、`budget`、`bond` 都不能低于 0；不能用负数制造隐藏债务。

## 3. 路线进入的最简酒馆同层仿真

### 3.1 为什么用同层 Markdown

当前目的只是验证玩法，不是验证代码接通。最小方案不需要：

- 隐藏楼层。
- `MESSAGE_SENT` 或 `/trigger`。
- memoryDB 写入。
- 新的手机页面。
- JS 解析器。

所有状态都放在同一个聊天层的 Markdown 面板里。每次正文前后保留一份状态块，下一轮由玩家或接手模型手工复制并修改。

### 3.2 路线判断块

进入路线前，先在同一条聊天里输出以下块：

```markdown
## 【V07 路线判断】

判断日期：2013-03-04
判断窗口：2013-03-04 ～ 2013-03-31

### 已确认事实
- [ ] 朱音压力已被看见
- [ ] 朱音路线入口已成立
- [ ] 单飞路线入口已成立
- [ ] 黑金共同反击意志已成立

### 当前 eligibility
- 单飞线：未满足 / 可进入
- 红坂朱音线：未满足 / 可进入
- 留下线：未满足 / 可进入

### 玩家选择
尚未确认

### 规则
只有玩家明确写出“路线确认：单飞线”或“路线确认：朱音线”，并且该路线为可进入，才可以锁定 choice。
```

玩家确认格式固定为：

```text
路线确认：单飞线
```

或：

```text
路线确认：朱音线
```

AI 必须先检查 `eligibility`，再回复以下结果之一：

- `路线已锁定：solo`。
- `路线已锁定：akane`。
- `路线未锁定：缺少事实……`。
- `路线已锁定，不允许改选；如需改线必须回滚到 choice 之前。`

### 3.3 路线进入后的第一条同层回复

路线确认成功后，AI 在同一聊天层输出短演出和进入状态，不启动完整开发周：

```markdown
## 【路线进入】

路线：单飞线 / 红坂朱音线
状态：已进入路线 session，尚未建立项目

### 进入场景
用 1～3 段正文说明为什么 User 现在必须面对这条路线的创作选择。

### 下一步唯一动作
当前没有项目：请先执行“定企划”，填写项目名、类型、平台和一句话卖点。
```

如果项目已经存在，则改为：

```markdown
状态：已进入路线 session，项目「第二作」已建立
下一步：直接安排本周六个行动；“定企划”不再出现。
```

## 4. 酒馆同层周计划模板

### 4.1 玩家填写模板

项目建立后，每周开头使用这一块：

```markdown
## 【开发周计划】

路线：solo / akane
项目：第二作
开发周：第 01 周
状态：planning

| 日期 | 行动 ID | 行动 | 目标 | 玩家意图 |
| --- | --- | --- | --- | --- |
| 周一 |  |  |  |  |
| 周二 |  |  |  |  |
| 周三 |  |  |  |  |
| 周四 |  |  |  |  |
| 周五 |  |  |  |  |
| 周末 | rest_date | 休整/约会 |  |  |

### 本周积分板（提交前预估）
progress：8 + 0
quality：8 + 0
fatigue：0 + 0
budget：16 + 0
bond：0 + 0

### 提交条件
- [ ] 五个工作日均已安排
- [ ] 周末行动已安排
- [ ] 合作/约会目标合法
- [ ] 每一天的玩家意图已填写或明确写“无”
```

### 4.2 提交流程

玩家填写完成后，必须明确发送：

```text
提交本周正文：确认以上六个行动，不再改选。
```

AI 先只回复冻结摘要，不立即扩写长正文：

```markdown
## 【本周行动已冻结】

周一：scenario / 独自完成
周二：art / 英梨梨
周三：programming / 独自完成
周四：polish / 诗羽
周五：music / 独自完成
周末：rest_date / 独处整理

本周周结算 ID：W01-LOCAL-001
状态：narrating
```

然后再生成正文。生成失败时，重复使用同一个 `W01-LOCAL-001`，不能重新抽取六个行动的效果。

### 4.3 注入正文的只读上下文

同层仿真中，可以把下面的文本手工放进提示词或作者注释：

```markdown
【本周开发行动上下文｜只读】
路线：solo
项目：第二作
周次：01
周一：scenario，目标=独自完成，意图=先定下核心冲突
周二：art，目标=英梨梨，意图=给她一个真正能燃烧的战场
周三：programming，目标=独自完成，意图=先让核心演出跑通
周四：polish，目标=诗羽，意图=检查角色动机是否被改薄
周五：music，目标=独自完成，意图=先确定情绪方向
周末：rest_date，目标=独处整理，意图=恢复并重新排期

写作要求：
1. 正文必须体现六个行动造成的工作节奏。
2. 可以出现失败、争执和临时调整，但不能替换已冻结的 action ID。
3. 不要在正文中自行宣布分数变化。
4. 不要自动确认新的路线事实。
```

### 4.4 正文后的手工结算块

正文完成后，AI 或玩家只按表格结算：

```markdown
## 【本周结算】

周结算 ID：W01-LOCAL-001
正文状态：completed
评价：A

progress：8 -> 19（+11）
quality：8 -> 21（+13）
fatigue：0 -> 7（+7，已接近高压线）
budget：16 -> 9（-7）
bond：0 -> 2（+2）

下周注意：fatigue >= 8 将触发明显代价；下周必须安排恢复或降低工作强度。
```

这段结算块是下一周唯一可读的项目状态来源。正文中的叙事不能覆盖它。

## 5. 路线专属进入仿真脚本

### 5.1 单飞线入口

入口必须体现“User 自己承担项目负责人责任”，但不能自动收编所有角色：

```markdown
## 【solo route entry】

User 已决定不把自己的创作未来交给现成体系。
当前可用资源：User 自己、临时合作、外包和经过正文确认的盟友。
限制：英梨梨、诗羽、惠都不是默认员工；黑金二人组保留独立创作者同盟。
下一步：若无项目，执行 concept；若已有项目，直接填本周六个 slot。
```

### 5.2 朱音线入口

入口必须体现“高压创作环境”，但不能把朱音写成万能老板：

```markdown
## 【akane route entry】

User 进入红坂朱音的高压创作环境。
可获得：更强的 brief、修改意见和创作强度。
代价：疲劳、截止压力、自主权和关系压力同步上升。
限制：朱音不能替玩家排六个 slot；英梨梨、诗羽仍不是默认员工。
下一步：若无项目，执行 concept；若已有项目，直接填本周六个 slot。
```

## 6. 手工仿真的注意事项

### 6.1 不要把三种状态混在一起

必须分开记录：

1. **路线事实**：例如“朱音路线入口已成立”，来源是正文证据。
2. **路线 choice**：玩家确认的 `solo` 或 `akane`，确认后锁定。
3. **项目状态**：项目名、progress、quality、fatigue、budget、bond。

路线事实不能由周计划行动直接点亮；周计划也不能反过来改路线 choice。

### 6.2 不要让正文代替结算

正文可以说“程序终于跑通了”，但真正的 `progress +3` 必须来自行动表。手工仿真中如果无法判断，就使用表格默认值，不让模型临场发明新数值。

### 6.3 不要让每周计划变成普通选项题

不要把六个 slot 压缩成 AI 输出的六个自由文本选项。玩家必须看到：

- 日期。
- action ID。
- 目标。
- 玩家意图。
- 当前积分板。
- 是否已冻结。

### 6.4 失败和重试

- 生成失败：保留同一份周计划和同一个周结算 ID。
- 重新生成：只重写正文，不重新抽行动效果。
- 玩家反悔：只能在冻结前改；冻结后要先明确回滚到冻结前。
- 发现目标不合法：整周仍是 `planning`，清除该日目标后重新填写，不自动替换。
- 任何“看起来像系统自动修正”的动作，都要在 Markdown 中留下说明。

### 6.5 同层仿真不等于生产接通

本仿真不能证明：

- SillyTavern preset 使用正确。
- 真实宿主楼层是否创建。
- `MESSAGE_SENT` 或 `/trigger` 是否触发。
- memoryDB 是否正确回滚。
- 生产 prompt 是否已经接入 weekly action context。

它只证明产品规则能在一次连续聊天里被人理解、填写和复盘。

## 7. 给 5.6 sol 的接手开发计划

### 阶段 A：只读设计审查

目标：确认本文件的产品规则，不写代码。

检查项：

- 是否接受“concept 一次性项目创建动作”。
- 是否接受“五个工作日 + 一个周末”的周计划单位。
- 是否接受路线判断和开发周计划分成两个视图/两个 Markdown 区块。
- 是否接受本版五项积分和软失败规则。

输出：一份简短的“接受 / 拒绝 / 修改”记录。

### 阶段 B：两条路线各跑一次酒馆同层仿真

必须各完成一份纯 Markdown 记录：

1. 单飞线：路线判断 → route choice → concept → 第 1 周六 slot → 正文 → 结算。
2. 朱音线：路线判断 → route choice → concept → 第 1 周六 slot → 正文 → 结算。

每份记录至少证明：

- 事实不足时不能进入路线。
- choice 由玩家确认并锁定。
- concept 只出现一次。
- 六个 slot 未排满不能提交正文。
- 周末不能选普通开发。
- 正文不会自行改分数。
- 失败重试不会重新抽周计划。

### 阶段 C：提出下一轮实现边界

只有 A、B 阶段被人工接受后，才可以提交下一轮代码范围。建议下一轮仍然从纯领域状态开始：

- `ProjectLifecycle`：`NO_PROJECT / PROJECT_CREATED`。
- `WeeklyPlan`：六个 slot、draft、冻结、重试和幂等。
- `RouteEntryDecision`：事实依据、choice、锁定和回滚信息。
- 纯函数结算器和确定性 fixture。

下一轮仍不应该同时接真实 AI、手机企划页、宿主楼层和 memoryDB。
