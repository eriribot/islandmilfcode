# 本地存档 v3：玩家手工测试说明 v0.3

> 本文是玩家实机验收清单，不是“已经测试通过”的报告。按本轮要求，自动测试、测试代码、构建和 TypeScript typecheck 均未执行；下列项目初始状态全部为 `not run`，只能由玩家实机结果改成 `passed` 或 `failed`。

## 1. 验收口径

本轮以“玩家能继续玩”为第一优先级。普通的旧档字段缺失、revision 竞争、本机桥暂时不可用、世界书读取失败或单个缓存对象损坏，应优先重试、回退或降级，不能让玩家卡在标题页，也不能让一次备份失败中断当前游玩。

唯一应当硬阻止写回的边界是：存档明确使用比当前程序更新的 archive/schema 版本。未来版旧聚合 payload 会按原样保留、列出和导出；无法安全封装的未来 archive 导入会整体拒绝。两种情况都不能进入后被当前版本降级覆盖。

每项测试都要同时观察三件事：

- 玩法结果：正文、状态、手机、图片和存档能否继续使用。
- 数据结果：刷新或重启后，最终可见内容是否仍然存在，revision 是否没有倒退。
- 降级结果：某个后端失败时，是否给出可理解提示并保留继续玩的路径。

不要把“控制台没有报错”当作通过，也不要把一次提示或降级本身当作失败；只有玩家结果与预期不一致才记 `failed`。

## 2. 测试前准备

1. 只测试复制出来的存档。先导出一份未修改备份，并把文件放到项目目录与酒馆数据目录之外。
2. 为浏览器、标准 SillyTavern（ST）、TT 桌面端和 TT 移动端分别建立独立测试副本，不要在多个环境共用唯一存档。
3. 开启开发者工具控制台并保留日志；记录浏览器或客户端版本、设备、操作时间、存档名与 `saveId`。
4. 需要破坏 root、修改 schema 或制造冲突的项目，必须使用专门的“可丢弃副本”。不得修改玩家唯一真实档。
5. 每个关键动作后等待界面保存提示稳定，再做刷新/重启验证。出现失败时，先保存控制台第一条错误和完整时间线，不要立刻连续重复点击。

建议先准备四类数据：

- 一个新建短档，包含至少 5 个完整正文楼层、一条手机草稿和一张可重生成图片。
- 一个长档，优先使用 300 层以上的副本；没有长档时至少准备 100 层。
- 一个仍为 v2 聚合格式的旧档副本。
- 一个启用了角色世界书、剧情库/角色卡和外部插件监听的环境。

## 4. 玩家实机项目

### P01 纯浏览器新档、保存和重开

步骤：

1. 确认没有安装或启用本机存档桥，刷新卡片并新建游戏。
2. 连续完成至少 5 个正文回合；期间修改玩家资料、一个状态值、手机草稿，并生成一张图片。
3. 等待自动保存，随后创建一次“手动存档”。
4. 回到标题页，先打开自动档，再打开手动档；最后彻底刷新页面后再打开一次。

期望：

- 标题页和正文首屏都能正常出现；缺少本机桥不会阻塞游玩，也不会无限显示“正在连接”。
- 正文顺序、当前时间/地点、角色状态、玩家资料、手机草稿和图片引用与保存前一致。
- 自动档与手动档都能进入；手动档是独立分支，之后修改其中一个不会改动另一个。
- 浏览器保存失败时允许显示降级提示，但当前会话仍能继续操作；恢复存储权限并刷新后可再次保存。

### P02 长档打开与尾部自动保存

步骤：

1. 打开 300 层以上的长档副本（最低 100 层），记录从点击进入到可操作正文的时间。
2. 在末尾新增 3 个回合，每回合等待自动保存完成；记录三次从正文完成到保存提示稳定的大致时间。
3. 滚动查看早期、中段和末尾楼层，再回到末尾继续一回合。
4. 刷新页面并重开该档，核对最后 4 个回合。

期望：

- 打开和保存期间页面没有长时间白屏、无响应或输入吞失。
- 末尾连续保存不应随着总历史长度明显逐次恶化；记录实测时间即可，本轮不预设硬毫秒阈值。
- 查看旧楼层不会改变当前状态，也不会触发无意义的新 revision。
- 刷新后尾部内容完整，早期楼层仍可查看。

### P03 v2 旧档迁移并继续玩

步骤：

1. 导入或放入一个 v2 聚合存档副本，确认它出现在存档列表。
2. 打开该档，核对正文、当前世界状态、玩家资料、手机消息/草稿、摘要/记忆和旧图片。
3. 即使界面显示迁移或降级警告，也继续发送一个新回合，随后等待保存并刷新重开。
4. 导出迁移后的档案备用。

期望：

- 普通缺字段、异常消息配对或可补默认值的问题只产生汇总警告，不把玩家挡在标题页。
- 已有正文不被静默删除或乱序；手机的“正在生成”瞬时状态不会从旧档复活。
- 新回合能生成并落盘；重开后仍在，迁移不会每次启动都重复破坏同一份档。
- 可确认的旧数据应尽量保留；无法确认的历史快照可降级，但必须明确提示，不能伪装成精确历史。

### P04 revision 冲突与多标签页

步骤：

1. 在 A、B 两个标签页打开同一个测试档，记录双方当前可见的最后一个楼层。
2. 在 A 新增一个回合并等到保存完成；B 保持旧页面，不刷新。
3. 在 B 触发一次不会产生正文的普通操作，再尝试手动保存；观察提示和控制台。
4. 刷新 B，确认能看到 A 的新回合；随后在 B 新增一个回合并保存，再刷新 A。
5. 重复两次快速切换和保存，最终彻底关闭两个标签页后重开。

期望：

- revision 只前进不倒退；旧页面不能把较新的 root 静默覆盖成旧历史。
- 冲突可以重试、重新加载或另存分支，不应造成整个存档不可进入。
- 同 revision、不同 root 的异常必须被识别，不能悄悄挑一个覆盖；最终至少保留一条明确可继续玩的最新分支。

### P05 手动存档分支

步骤：

1. 在自动档末尾记下当前状态与最后一段正文，创建“手动存档”。
2. 进入手动档，做一个明显不同的选择并生成新正文。
3. 回到标题页打开原自动档，再打开手动档。
4. 分别导出两档，记录文件名和 `saveId`。

期望：

- 创建分支本身不需要重写或丢弃源档历史。
- 两个档的历史截止点相同，但后续正文、状态和 revision 独立。
- 手动档损坏或保存失败不得反向破坏源自动档。

### P06 回溯到玩家输入

步骤：

1. 选一个会明显改变时间、地点、好感或手机内容的完整回合，记录该回合前后的状态。
2. 从该楼层菜单执行“回到输入/回溯到玩家输入”。
3. 检查输入框、正文尾部、状态、手机消息与图片；修改输入后重新发送。
4. 等待保存，刷新重开。

期望：

- 原玩家输入回到编辑器；目标 assistant 及其后的楼层被截断，不残留重复 user 消息。
- 状态恢复到该回合开始前的快照，包括合法的零值、手机边界和玩家资料；不能保留被撤销回合的后果。
- 新生成内容成为新的尾部，刷新后不会把已截断旧分支重新拼回来。

### P07 回溯到已完成楼层

步骤：

1. 选择历史中一个已完成的 assistant 楼层，记录该楼层结束后的状态。
2. 执行“回溯到此处/保留完成楼层”，确认后续楼层消失。
3. 在该点继续发送一个新回合，保存并重开。

期望：

- 选中楼层本身保留，只有其后的楼层被截断。
- 当前状态精确恢复为该楼层的 after 快照，而不是回到 before，也不是沿用截断前的最新状态。
- 继续玩和自动保存正常，重开后仍是新分支。

### P08 正文重生成与纯文本删除

步骤：

1. 对一个历史 assistant 楼层执行“重新生成正文”。
2. 等待新正文完成，比较原输入、楼层数量、状态和图片引用。
3. 保存、刷新并重开；再做一次快速重生成，观察是否出现重复生成。
4. 另选一个中间楼层，先记录当前时间、地点、好感、手机、摘要/记忆和它之后的正文，再执行“删除该楼层”；保存并刷新重开。
5. 再发起一次正文生成，在流式卡尚未产生可见文字时立刻删除它，确认菜单和空卡同时消失；刷新后确认它没有复活。

期望：

- 原玩家输入只复用一次；旧 assistant 及其后续被正确截断，新 assistant 替代它。
- 旧回合产生的状态先回到 before，再由新正文推进；不会叠加两次结果。
- 一次操作只启动一次生成；刷新后只保留新的分支。
- “删除该楼层”只删除点中的文本卡片：之后的正文和当前权威状态不回滚、不裁剪；刷新后目标卡片不复活。删除 user 后保留下来的 assistant 不应额外显示一张空白 System 卡。
- 删除空流式卡会终止对应任务并立即持久化；界面不残留旧菜单或幽灵卡片。

### P09 图片重生成与图片恢复

步骤：

1. 选择带图片、负面提示词或重生成上下文的楼层，执行图片重生成。
2. 等待图片真正显示后立刻手动保存，并彻底刷新或重启客户端。
3. 打开原档和由它创建的手动分支，分别查看图片。
4. 在桥接环境临时断开本机文件访问后再看一次，并恢复连接。

期望：

- 重生成只替换目标图片，不改变正文楼层、状态或其他图片。
- 图片数据写完后才算保存成功；重启后不能只剩 asset id 或破图。
- 分支仍能引用已存在的图片；暂时读不到本机图片时可使用浏览器副本或占位提示，不能阻塞正文游玩。
- 普通清理流程不能误删仍被当前 root、previous root 或其他分支引用的图片。

### P10 标准 ST 本机桥

步骤：

1. 按项目现有方式安装并启用 `savesolt/IslandMilfCode本机存档桥.js`，确认桥握手成功。
2. 新建或打开测试档，完成 3 个回合，等待每次自动保存；创建一次手动档。
3. 完全退出 ST，再启动并打开两档；检查正文、状态和图片。
4. 临时令桥不可用，继续一个回合并保存；恢复桥后再保存一次。
5. 若测试目录中同一 `saveId` 同时有 v2 bundle 与 v1 legacy，分别从恢复列表选择两项，确认第一次优先恢复所选来源；再单独破坏所选候选，确认才会回退另一份。
6. 在可丢弃副本中制造“本机 registry revision 高于浏览器当前 revision”的同 `saveId` 场景，再点一次手动本机备份。
7. 打开浏览器 F12 控制台并筛选 `[archive-bridge]`；对同一个 revision 连续点两次手动本机备份，再完成一个新回合并等待自动保存。
8. 同时查看 SillyTavern 终端里的 `Uploaded file`：分别记下首次手动备份、重复手动备份和新回合保存的文件名及总条数。

期望：

- 浏览器提交先成立，本机备份随后完成；本机备份慢或失败不会撤销浏览器已保存结果。
- 重启后可从当前 root 恢复；桥恢复后能继续备份较新的 revision，不要求玩家清库重来。
- 旧 revision 不得把 registry 回滚；相同 root 的重复提交不应丢掉真实 previous root。
- v1/v2 同名候选不能“点 v1 却总是恢复 v2”；候选损坏时的自动回退仍要保留正文主数据。
- 本机已有更高 revision 时应明确提示“本次未覆盖”，不能显示“备份完成”，也不能每分钟无限重试；浏览器里的当前游戏仍可继续玩和保存。
- 每轮同步只出现一条 `[archive-bridge] 备份成功` 或一条 `[archive-bridge] 备份失败`；成功项中 `attempted = uploaded + reused`，并能分别看到对象、图片、root、registry 的计数。`jsonUploads + imageUploads = fileUploads`，用于和真实写入次数对照。
- 已存在的同 hash `state`、`summary`、`memory` 与同一图片不能再次出现在终端 `Uploaded file` 中；新增或确实变化的 chunk、index、root、registry 仍可出现。
- 把某个已备份图片文件临时移走后再保存，该图片应计入 `uploaded` 并被补回，不能为了显示 `reused` 留下破图。
- 若浏览器 IndexedDB 中原本就缺少某个被引用图片，汇总应显示 `missingImages > 0` 和 `degraded: true`，但正文、状态和 registry 仍应保存成功，玩家不能被图片附件卡住。

### P11 TT 桌面端与移动端本机桥

步骤：

1. 在 TT 桌面端重复 P10 的新建、3 回合、手动分支、重启恢复流程。
2. 在 TT 移动端重复同一流程，并额外执行一次切到后台 30 秒再回前台。
3. 移动端网络或文件桥暂时断开时继续一回合，恢复后再次保存并重启。

期望：

- 两个平台的首次渲染、保存和恢复均可完成；移动端切后台不会让“正在生成/正在保存”永久卡住。
- 多个只读对象请求不会因为排队而在尚未开始时统一超时。
- 桥失败时仍保留浏览器主存档；桥恢复后重试，不要求删除现有档。

### P12 当前 root 损坏时回退 previous root

此项优先在本机桥副本上执行，因为 bridge registry 会记录当前与 previous root。操作前复制整个测试档目录。

步骤：

1. 连续完成并确认至少两次 v3 保存，记录最新和前一次 revision。
2. 关闭客户端，备份 `islandmilfcode-archive-registry-v3.json` 及对应对象目录。
3. 仅在可丢弃副本中，删除或破坏 registry 当前 `rootHash` 指向的 root 对象；不要修改 `previousRootHash` 对象。
4. 重启并进入该档，观察提示、可见的最后楼层和 revision；随后另存为新分支，不要覆盖原损坏副本。

期望：

- 当前 root 缺失或校验失败时，读取 previous root，并明确标记“已降级/回退”，而不是显示空档或卡死。
- 最多丢失最后一次未能恢复的提交；previous root 对应的正文和状态完整可玩。
- 程序不能把损坏当前 root 当作空白新档并自动覆盖；玩家可导出或另存恢复结果。

### P13 世界书缓存：成功、连续失败与合法空结果

步骤：

1. 绑定一个含剧情目标和角色卡目标的世界书，进入存档并确认内容已加载；保存并重启，验证缓存可用于首屏。
2. 在世界书内容数量不变的情况下修改一条正文，再刷新绑定，观察剧情库/角色卡是否更新。
3. 临时让世界书 API 连续失败至少 5 次，每次回到正文继续玩一回合；记录提示频率和缓存内容。
4. 恢复 API，确认新内容可替换旧缓存。
5. 再绑定一个“调用成功但目标列表合法为空”的世界书并刷新。

期望：

- 缓存只用于相同角色与相同世界书绑定；不能把上一存档或另一套世界书内容串进当前档。
- 内容变化即使条目数量不变也能被识别；加载失败时保留最近一次成功缓存并允许继续玩。
- 多次失败可汇总提示和重试，不能把缓存误清空，也不能让进入存档永久停在 restoring 状态。
- 合法空结果必须被当作一次成功更新：清空对应派生库，不得用旧缓存假装仍有内容。

### P14 外部插件事件与生命周期

步骤：

1. 启用现有外部插件监听，依次执行：进入存档、生成正文、自动保存、手动分支、回到标题页、重新进入。
2. 在正文生成结束后但自动保存尚未稳定时快速回标题页，再进入另一个档。
3. 在一次生成中途执行已提供的取消/导航操作，观察旧任务是否还向新档写消息或状态。
4. 记录插件收到的事件名称、次数、顺序与关联 `saveId/runId`。

期望：

- 生命周期事件携带正确的当前存档身份；一次用户动作不产生重复完成事件。
- 回标题页会先处理当前可保存内容，再使旧生成/手机任务失效；旧任务不能在新档中追加正文或覆盖状态。
- 插件抛错或缺席不能阻断存档与正文主流程。

### P15 导出、导入与跨环境恢复

步骤：

1. 从含长历史、图片、手机草稿、摘要/记忆和手动分支的 v3 档导出单档 JSON。
2. 在全新的浏览器 profile 或另一测试环境导入，确认列表项后进入存档。
3. 核对首、中、尾楼层、当前状态、图片和分支；新增一回合并再次导出。
4. 从存档列表分别逐项导出一个 v2 副本、一个 v3 档和一个只读 future `single-save`，确认下载文件对应玩家点中的 `saveId`。
5. 尝试导入缺少一个非关键可选对象的副本，观察是否给出降级提示并尽量可玩；不要破坏原备份。

期望：

- 导出在待写任务落盘后才读取，不产生缺尾楼层的半包。
- 导入后 `saveId/runId`、楼层顺序、状态、摘要/记忆和图片引用一致；可以继续生成与保存。
- 同名冲突应有明确结果，不能静默把较新 revision 换成较旧内容。
- 非关键对象异常优先降级；关键 floor/index 缺失必须明确报告，不能伪装为完整导入。

### P16 future schema 只读、不覆盖

步骤：

1. 复制一份 `single-save` 旧聚合备份，给它改成全新的测试 `saveId/runId`，把 `payload.saveDataSchemaVersion` 改成明显高于 3 的值，并加入一个当前程序不认识的字段。
2. 导入该副本，确认它能留在列表中；点击进入应看到只读提示。随后导出该项并比较未知字段。
3. 重启后再次从存档列表导出该项，确认未知字段仍在且没有被改写。
4. 另复制一份 `archive-v3` 文件，把 root 的 archive/schema 版本改成明显高于 3，再尝试导入；保留这份外部原文件用于逐字比较。
5. 若测试环境本来就有由更新版本写入浏览器的 future archive，确认它仍在列表；点击进入应只读阻止，点击导出应得到 `archive-future-readonly` 救援包，且 root/meta 与可识别对象未经当前版本 normalize。
6. 再复制一份结构完整的旧聚合档，只把显式 schema 标签改成非标准字符串（例如 `third-party-beta`），保留 `gameState + chatLog`；导入后确认仍可进入、继续一回合并另存。

期望：

- 程序明确拒绝把 future schema 当当前 v3 打开并写回；这是本轮唯一需要硬阻止的边界。
- future `single-save` 仍允许列出和原样导出，未知字段和值保持不变；future archive 若无法安全封装则在导入前整体拒绝，外部原文件不受影响。
- 已经存在浏览器中的 future archive 可导出只读救援包；缺少的未来对象要写入 warnings，不能假装是可由当前版恢复的完整 v3 包。
- 不能因为同 `saveId` 还存在 v2 副本，就悄悄打开 v2 并在后台覆盖 future root。
- 非标准标签本身不构成硬阻断：只要旧聚合结构是当前 decoder 明确认识的，优先让玩家进入；只有明确高于当前版本的数值边界才只读。

### P17 v3 文件数量、两代保留与删档联动

这一项在可丢弃的副本中执行；操作前备份 `user/files/islandmilfcode-archive-registry-v3.json` 和现有 v3 文件。

步骤：

1. 重启宿主并更新/重新导入本机桥，完成一次自动存档；在 F12 展开唯一一条 `[archive-bridge] 备份成功`。
2. 记录 `archiveLayout`：已打宿主目录补丁应为 `subdir-v1`，原版宿主应为 `flat-v3`；两者都应能继续玩。
3. 对同一存档连续完成 5 个回合，每轮等待备份成功；备份成功只代表 registry 已安全提交，看到 `gc.status: scheduled/running` 后再留出后台清理时间，记录第 1 轮和第 5 轮的 v3 JSON 数量。
4. 展开最后一条成功汇总，记录 `gc.status` / `gc.deleted` / `gc.retainedShared` / `gc.failed` / `gc.pendingTombstones` / `gc.pendingFiles` / `gc.registryLock`；也可在 registry 的 `lastGc` 查看最近一批结果。
5. 完全重启 ST/TT，进入存档，检查最新楼层和上一 revision 的恢复能力，再继续一回合。
6. 新建一个手动分支，保存后删除原存档；等待唯一一条 `[archive-bridge] 本机删除成功`。
7. 重启后确认原存档不会被本机恢复列表带回，手动分支仍可进入，共享楼层和图片正常。
8. 标准 ST 检查 `data/logs/file-operations-YYYY-MM-DD.log`：上传/删除明细应在文件中，终端不应逐文件刷 `Uploaded file` / `Deleted file` / `Deleted image`。

期望：

- 新 revision 不再无界保留所有历史 root/state/index/chunk；每个存档只保留当前与上一两代恢复点，共享内容只保留一份。
- 文件数量可因本轮真正新增的尾块/索引短暂波动，但不应每回合固定只增不减。
- 回收只处理无任何活动 root 引用的 v3 root/index/state/chunk JSON；不删 v1/v2 备份，不自动删图片实体与 image manifest，也不为了减少文件数删楼层或截断正文。
- `gc.status: deferred/partial` 时存档和游玩仍应成功；只是物理垃圾留待下次重试。
- 要实际删除旧 JSON，`gc.registryLock` 应为 `web-locks`；旧 WebView 若显示其他值，应保持可玩并把 GC 留在 `deferred`，不要强行删除。
- 删档后已排队的旧备份不得复活该存档；其他分支共享的对象不得被删除。
- 早期崩溃时已经脱离 registry 链的孤儿文件可能仍保留；本轮先验证持续增长已停止，不对真实玩家目录做猜测式批量删除。

## 5. 失败后的最小复现顺序

发现问题时不要只写“存档坏了”。按下面顺序保留证据：

1. 立即停止继续操作该副本，记下最后一个成功动作与第一个异常动作。
2. 截图当前页面、保存提示和存档列表；复制控制台第一条错误及其完整堆栈。
3. 记录平台、版本、后端模式、`saveId/runId`、操作时间、最后可见楼层和是否使用世界书/桥/插件。
4. 导出仍可导出的档案，并备份 bridge registry/对象目录或浏览器 profile；不要清空 IndexedDB 后再报告。
5. 在另一个副本上只重复最短动作序列，确认是否稳定复现。
