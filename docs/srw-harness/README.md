# SRW Harness

## 一句话定义

SRW Harness 是一套“机战母舰式 AI 协作架构”：人类驾驶员坐在驾驶舱里做判断、批准和发射，AI 作为副驾驶、参谋、整备班与测试班，负责拆解、草拟、巡检、复盘和提出升级方案。

它不是让 AI 自动接管项目的 autopilot，也不是把任务塞进 `.codex-loop` 里长跑。SRW Harness 的核心是让驾驶员在正确仪表盘上做正确批准。

## v0.1 文档包

第一版母舰 Harness 由四份文档组成：

- `README.md`：母舰总纲，定义 SRW Harness 是什么、不是什么。
- `SRW_MOTHERSHIP_HARNESS_V0_1.md`：v0.1 可执行规格，定义一次任务如何从侦察到复盘。
- `COCKPIT_APPROVALS.md`：驾驶舱批准门，定义哪些动作 AI 可直接做、哪些必须等驾驶员发射。
- `UNIT_REGISTRY.md`：机体登记表，登记 islandmilfcode、webgame-ui、bridgeapi_shujuku 的职责、接口和失败模式。
- `ARSENAL.md`：武器库，沉淀消息污染防线、世界书裁剪、同层桥接、模块分层等打法。

v0.1 的目标不是全自动，而是让每次协作都能明确回答：当前开哪台机体、要打哪个目标、谁按发射键、怎么确认命中。

## 为什么不是 `.codex-loop`

`.codex-loop` 适合处理可拆分、可验证、低歧义的连续工程任务，例如批量整理文档、重复执行测试、按固定任务清单推进实现。

SRW Harness 处理的是更上层的协作母舰：

- 多项目、多机体之间的指挥口径。
- 人机交互批准门。
- 需求、代码、世界书、桥接 API、UI、测试与复盘之间的接驳关系。
- AI 何时只能建议，何时可以动手，何时必须停在驾驶员批准前。

所以 `.codex-loop` 只能作为 SRW Harness 的可选外挂模块，不能成为核心。它像自动巡航、补给线或维修班流程，不是驾驶员本人，也不是母舰指挥权。

## 核心原则：驾驶员手操优先

SRW Harness 默认手操优先。最稳的协作方式不是让 AI 全自动冲，而是把每个高价值动作变成清楚的驾驶员批准点。

基本原则：

- 驾驶员保留发射键。
- AI 可以拆解、比较、草拟、验证、提示风险。
- AI 不应擅自扩大任务边界。
- 涉及剧情方向、世界观设定、角色关系、数据结构、跨项目协议、不可逆写入时，必须请求驾驶员确认。
- 自动化只能服务手操流程，不能反过来吞掉手操判断。

一句话：AI 是副驾驶、参谋、整备班；驾驶员才是机师。

## 母舰编制

SRW Harness 用“母舰 + 机体 + 接驳舱 + 武器库 + 战斗记录”的方式组织项目资产。

### 母舰：SRW Harness Core

母舰负责定义协作规程：

- 驾驶员批准门。
- 当前任务驾驶舱。
- 机体接入标准。
- 可复用武器库。
- 战后复盘与升级记录。

母舰不替任何机体写死业务逻辑。它提供指挥台、检查单和批准协议。

### 机体：可被调度的项目或模块

机体是实际作战单位，例如：

- `islandmilfcode`：当前主机体，负责手帐式楼层阅读、续写、回溯、重新生成、变量读取、状态驱动 UI。
- `webgame-ui`：可作为独立驾驶舱或战斗界面机体，承载更游戏化的操作面板。
- 其他角色卡、前端模块、记忆库模块、剧情路由模块，都可以作为子机体接入。

每个机体都必须有自己的边界说明：输入、输出、状态、失败模式、测试方式、驾驶员可见控制项。

### 接驳舱：bridgeapi_shujuku

`bridgeapi_shujuku` 更像母舰和酒馆原生楼层之间的接驳舱。它的价值不在于 iframe 里自嗨，而在于把 UI 操作接回真实宿主聊天楼层、世界书扫描、数据库更新、正则深度和助手生成链路。

关键不变量：

- 宿主真实聊天楼层是权威记录。
- 隐藏 real user / assistant 楼层用于承载原生规划与更新链路。
- UI 状态不能替代宿主状态。
- 桥接失败时必须暴露给驾驶员，而不是假装生成成功。

### 驾驶舱：当前任务 UI

驾驶舱是驾驶员实际操作的界面。它可以是 Codex 当前线程、同层卡 UI、webgame-ui 页面、检查清单文档或测试面板。

驾驶舱必须回答四个问题：

- 我现在在操作哪台机体？
- 这次行动会改什么？
- 哪些动作需要我批准？
- 成功或失败如何被验证？

### 武器库：Arsenal

武器库保存可复用的打法、模板和防线，例如：

- 消息污染防线：`lastSummarizedIndex` 只增不减，除非超过实际消息总数。
- 世界书裁剪：代码做裁判，世界书说话。
- `activeCardIds` 控制器：由 TS 集中判断实际参与角色，避免关键词误触发完整角色卡。
- 同层桥接：使用真实宿主楼层，不把 iframe 内部状态当最终事实。
- 模块分层：入口、状态、变量、提示词、动作、渲染分层，避免继续把业务塞进 `index.ts`。

武器库不是硬套模板。每次出击前，AI 应根据当前机体选择合适武器，并说明为什么用它。

### 战斗记录：Telemetry / Postmortem

战斗记录用于让系统越打越稳：

- 本次任务目标。
- 实际改动。
- 执行过的验证。
- 发现的风险。
- 驾驶员批准过的决策。
- 可沉淀进武器库的模式。

战斗记录不追求长篇报告，重点是能让下一次接手的人或 AI 快速恢复战场态势。

## 手操批准门

SRW Harness 把任务分成三类批准等级。

### A 级：AI 可直接执行

满足以下条件时，AI 可以直接动手：

- 只读检查、搜索、定位。
- 新增不影响运行的说明文档。
- 小范围、可逆、局部文件修改。
- 已有明确测试命令且不会写生产数据。
- 变更不跨越模块边界。

即便可以直接执行，AI 也应在动手前简短说明要改什么。

### B 级：AI 草拟，驾驶员批准后执行

以下动作需要驾驶员批准：

- 改变交互流程。
- 调整提示词主口径。
- 修改角色关系、剧情路线、世界观事实。
- 引入新依赖或新服务。
- 改动跨模块接口。
- 批量迁移数据或文件。
- 把手操流程升级成自动化流程。

AI 可以先给出推荐方案、风险、回滚方式和验证方法，但不能默认执行。

### C 级：必须停火等待

以下动作必须停在批准前：

- 删除、覆盖、回滚用户未明确要求的内容。
- 生产数据写入。
- 公开发布、推送、合并、部署。
- 不可逆迁移。
- 可能改变角色卡长期设定或玩家存档语义的动作。
- 任何把驾驶员批准门绕开的自动化。

这类动作不允许用“我猜用户应该想要”来跳过。

## Mode Router

SRW Harness 的模式路由用于判断当前该以什么姿态工作。

| 模式 | 触发场景 | AI 职责 | 驾驶员职责 |
| --- | --- | --- | --- |
| 侦察模式 | 读代码、读文档、定位问题 | 找边界、找不变量、列故障面 | 决定是否进入实现 |
| 整备模式 | 写文档、清单、协议、模板 | 草拟结构、补充检查项、沉淀武器库 | 批准口径 |
| 出击模式 | 实现明确功能或修复 | 小步修改、运行验证、报告结果 | 批准高风险动作 |
| 接驳模式 | islandmilfcode、webgame-ui、bridgeapi_shujuku 联动 | 定义输入输出、桥接失败面、测试链路 | 批准跨项目协议 |
| 复盘模式 | 修 bug 后总结经验 | 提取可复用模式、更新 Arsenal | 判断是否纳入母舰标准 |
| 自动化外挂模式 | 批量低歧义任务 | 生成任务队列、执行可验证步骤 | 逐级批准启用自动化 |

默认从侦察或整备开始。只有任务边界清楚、风险可控、验证明确时，才进入出击或自动化外挂模式。

## 当前第一主机体：islandmilfcode

`islandmilfcode` 当前适合作为 SRW Harness 的第一主机体，因为它已经同时具备 UI、状态、变量、提示词、消息楼层、记忆库和剧情路由等复杂接口。

现有边界应被 SRW Harness 保护：

- `index.ts` 只做入口装配、初始化、生命周期绑定和渲染调度。
- `state` / `store` 管理本地状态。
- `variables` / `adapter` 统一封装变量读取和写回。
- `prompt` / `message-format` 负责正文抽取、回复清洗和提示词拼装。
- `actions` 负责发送、流式生成、通知、回溯、重新生成。
- `render` 只负责状态到界面的映射。

核心作战能力：

- 楼层阅读。
- user + assistant 楼层计数。
- 回溯楼层输入。
- 重新生成该楼层。
- 重新生成成功清空 draft。
- 重新生成失败保留 draft。
- 右键楼层菜单工作流。

SRW Harness 对它的第一要求不是“继续加功能”，而是让驾驶员能稳定看见状态、批准动作、验证结果。

## 自动化边界

自动化在 SRW Harness 里只是一种工具，不是方向盘。

允许自动化：

- 重复运行测试。
- 生成候选检查清单。
- 整理战斗记录。
- 对低风险文件做格式化。
- 根据已批准的任务队列逐项执行。

禁止自动化：

- 自动替驾驶员批准剧情、角色、协议或数据结构方向。
- 自动扩大任务范围。
- 自动删除或回滚用户改动。
- 自动把一次性脚本固化成长期机制。
- 自动绕过宿主楼层、世界书或数据库的真实更新链路。

判断标准：如果一个动作失败后需要驾驶员解释世界观、剧情因果、接口语义或存档后果，那它就不该自动执行。

## 人机交互协议

每次 SRW Harness 行动应遵循下面的轻流程：

1. AI 标明当前模式与目标。
2. AI 识别机体、接驳点、不变量和失败模式。
3. AI 区分可直接执行项与需批准项。
4. 驾驶员批准高价值动作。
5. AI 执行小步变更并运行验证。
6. AI 汇报已执行、已检查、仍是假设的内容。
7. 可复用经验进入 Arsenal。

这不是官僚流程，而是驾驶舱仪表。仪表越清楚，驾驶员越敢手操。

## 下一步迭代

建议下一步不要急着做自动化，而是继续把三类文档实战化：

- `COCKPIT_APPROVALS.md`：驾驶员批准门清单，细到每类动作该停在哪里。
- `UNIT_REGISTRY.md`：登记 islandmilfcode、webgame-ui、bridgeapi_shujuku 等机体的输入、输出、失败模式和验证方式。
- `ARSENAL.md`：沉淀消息污染防线、世界书裁剪、同层桥接、模块分层等可复用打法。

等这三块稳定后，再考虑是否接入 `.codex-loop` 或其他自动化外挂。自动化必须从母舰协议派生，不能反过来定义母舰。
