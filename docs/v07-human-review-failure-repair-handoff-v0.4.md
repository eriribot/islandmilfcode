## 2. 人工验收结论

### 2.1 路线语义误判

人工复现：玩家明确表达自己会留在 `blessing software`，Gemini 3 Flash 仍把单飞相关变量判为成立。

结论：当前路线事实写入链虽然是真实写入，但语义结果不可靠，不能作为正式流程使用。

必须保护的合同：

- “User 明确继续留在 blessing software”与“User 已脱离 blessing software 独立创作”在同一终态下互斥。
- 明确留下时，`solo_route_open=yes` 和 `user_exit_commitment_grounded=yes` 都必须禁止提交。
- 正反证据同时存在或终态无法唯一确定时，必须 fail closed：保持原值/`unset`，或要求玩家确认。
- 不能仅凭“自己做游戏”“独立创作”等词语反推已退出、已交接或已正式单飞。

### 2.2 玩家兜底需求被错误实现

实际实现的是设置页总开关“自动路线事实核对”。它只能整体开启/关闭自动审查。

玩家真正需要的是逐变量兜底：

- 显示每个路线 flag 的 `yes / no / unset`。
- 显示标签、含义、证据、最后修改时间和来源楼层。
- 玩家可手动设置单个 flag。
- 玩家可撤销最近一次错误写入或恢复 `unset`。
- 出现互斥/争议时可以逐项确认或拒绝。
- 手动值与自动值的优先级、审计记录和后续自动更新规则必须明确。

这是需求理解错误，不能通过改总开关文案解决。

### 2.3 判定器启停边界错误

当前配置：

- `plot-state-machine/v07.ts` 的 `proposalWindow.start = 2013-02-25`。
- 当前 `proposalWindow.end = 2013-03-31`。
- `promptWindow.start = 2013-03-04`。
- 当前实现把 `2013-03-04` 当成路线选择开始日，而不是自动判定关闭日。
- 正文后自动审查主要按日期窗口决定是否运行，并未形成“第七卷开始时开启、到 2013-03-04 停止”的硬门禁。

用户纠正后的目标范围：自动事实判定从第七卷开始启用，到 `2013-03-04` 关闭。也就是 `2013-03-04` 当天不再运行该自动判定器。

下一轮需要先定义可靠的“第七卷开始”来源，不能仅因状态机文件名是 `v07.ts` 就宣称已经限定第七卷。推荐门禁语义：

```text
currentVolume === V07（或当前事件属于 V07）
AND currentDate >= V07_START_DATE
AND currentDate < 2013-03-04
```

`V07_START_DATE` 应复用剧情库/卷定义的权威起点，不要随意另造日期。若卷号与日期冲突，应 fail closed，并留下调试记录。

### 2.4 毕业系统错误

截图人工反馈：毕业典礼反复把一群角色写成共同毕业，其中波岛出海和高年级角色一起毕业在时间线上明显错误。用户进一步澄清：问题不是“持久化没有及时刷新”，而是“拿持久化状态判断学年”这个设计方向本身不对。学年真值必须来自剧情日期对应的学年 count。

进一步检查后确认了一个更直接的毕业典礼重复原因：代码把“一次性毕业典礼事件”和“毕业后持续身份”混用了同一种 `date >= graduationDate` 范围判断。

已确认的代码事实：

- `school-calendar/identity-resolver.ts` 已内置出海生日 `1997-05-05`。
- 出海的教育步骤是 `初3 -> 丰之崎 1年C班`。
- 在 `2013-03-04`，身份解析有能力把出海视为中学初三，而不是高中毕业生。
- `school-calendar/prompt-adapter.ts` 使用 `if (date >= UTAHA_GRADUATION_DATE)` 注入“2013-03-04 是诗羽毕业典礼日”的提示。因此从 `2013-03-04` 开始，`2013-03-05`、`2013-04-01` 乃至后续每天都会重新收到包含“毕业典礼日”的提示。这不是存档每天累积一次，而是每次生成时都重新命中同一个 `>=` 条件。
- `school-calendar/identity-resolver.ts` 使用 `profile.graduationDate && date >= profile.graduationDate` 将诗羽持续解析为毕业生。这个持续状态本身正确；错误是把它与只应发生一次的毕业典礼事件混为一谈。
- 当前没有显式的 school-year `count` 字段；年级推进是在 resolver 内用日期直接计算。
- `school-calendar/state-sync.ts` 会把派生结果持久化为 `schoolIdentityKind`、`schoolIdentityLabel`、`schoolCalendarSyncedAt`。
- `state/saves.ts` 会保存并恢复上述派生字段。
- `render.ts` 和 `phone/render.ts` 会读取持久化的 `schoolIdentityLabel` 用于显示；它只能作为显示缓存，不能作为学年权威值。
- `relationship.ts:getCharacterAnchorGuidance()` 在调用方没有传入 `currentTime` 时，会回退使用 `target.meta.schoolCalendarSyncedAt` 作为关系/学年计算日期。这是已发现的“用持久化同步时间参与学年判断”风险点，下一轮必须审计并消除这种权威回退。
- 当前没有逐角色的毕业典礼参与资格集合，也没有强制禁止非本届学生被写成共同毕业。
- 现有仿真只验证出海在 `2013-04` 是一年级，没有保护“出海在 2013-03-04 不得作为毕业生”。

因此当前至少有三个需要分别修复的失败层：

1. 事件/状态边界：毕业典礼是 `2013-03-04` 的一次性事件，毕业生身份是该日之后的持续状态；当前提示适配器没有分开。
2. 学年判断层：部分调用链可能把持久化的同步日期/派生身份当成学年判断依据；这是错误的权威来源。
3. 即使身份正确，正文层也没有毕业参与资格硬约束。

持久化字段可以服务 UI 缓存或审计，但不得决定角色当前学年。即使缓存值与当前日期碰巧一致，也不能把它当成正确设计。

### 2.5 用户要求的学年 count 匹配模型

把 2012 学年视为基准，按每年 `04-01` 的学年边界计算偏移：

```text
2012 学年（直到 2013-03-31） -> schoolYearCount = 0
2013-04-01 起                 -> schoolYearCount = 1
后续每跨过一次 04-01          -> count 再加 1
```

核心不是把 count 当作只增不减的点击计数，也不是从存档里的旧身份猜当前学年；而是每次直接用当前剧情日期确定性匹配 count，再由“基准教育身份 + count”派生当前年级。持久化的 `schoolIdentityLabel`、`schoolIdentityKind`、`schoolCalendarSyncedAt` 不得参与真值裁决。

权威关系应固定为：

```text
currentStoryDate
-> schoolYearCount
-> 基准年级 + count
-> 当前学年/毕业资格
-> 可选的显示缓存
```

禁止反向使用：

```text
持久化 label/kind/syncedAt
-> 猜当前学年或毕业资格
```

需要覆盖的例子：

- `2012-12-07`：`count=0`。
- `2013-03-04`：仍为 `count=0`。
- `2013-03-31`：仍为 `count=0`。
- `2013-04-01`：切换为 `count=1`。
- 在 `count=0` 保存后跳转/读入 `2013-04-01`：必须直接按当前剧情日期得到 `count=1`，不能向持久化身份询问学年。
- 在 `count=1` 的存档回退到 2012 日期：如果系统允许时间回退，必须按当前剧情日期得到 `count=0`，不能沿用持久化身份。

下一轮应保护的合同：

- 毕业典礼提示只允许在 `date === 2013-03-04`（或权威毕业事件 ID 正在进行）时出现。
- `date > 2013-03-04` 只能表达“诗羽已经毕业”，不得继续表达“今天正在举行毕业典礼”。
- “在毕业场景中出现”不等于“作为毕业生参加毕业”。
- 每位被描述为毕业的人都必须通过当日、学校、学届/年级资格检查。
- `2013-03-04`：诗羽可作为毕业生；出海不得作为毕业生。
- 英梨梨、惠和 User 也必须按各自实际学届逐人判断，不能因为属于主要角色或在上下文中出现就默认一起毕业。

## 4. 失败原因：已确认与推测分离

### 4.1 已确认原因

1. 证据来源校验与语义正确性校验被混为一谈。现有校验只保证引用来源真实。
2. stay/solo 互斥只存在于自然语言含义，没有成为提交器的硬不变量。
3. 自动审查的启停窗口与用户要求相反：当前在 `2013-03-04` 后仍运行，目标是从第七卷开始并在该日关闭。
4. 玩家只能关闭整个自动审查，不能修正单个错误变量。
5. `prompt-adapter.ts` 用 `date >= 2013-03-04` 注入毕业典礼提示，导致之后每一天都被当成仍处于毕业典礼语境；一次性事件与持续身份没有分层。
6. 当前存在持久化的学校身份/同步日期字段，且 `relationship.ts` 在缺少 `currentTime` 时会用持久化 `schoolCalendarSyncedAt` 作为学年关系计算日期；学年不应由持久化状态判断。
7. 毕业系统没有逐角色毕业参与资格过滤。
8. 游戏开发面板没有接入正文、宿主消息、插件或数据库剧情流程。

### 4.2 高概率推测，实施前需用日志/复现验证

1. Gemini 3 Flash 可能把“独立创作想法”或“自己做游戏”作为路线关键词，忽略同段落中的留下、未退出或否定事实。
2. 两次同模型复核共享相同偏差，因此重试会重复错误，而不是纠错。
3. 路线 flag 分别判断后直接合并，缺少全局终态一致性检查，可能允许语义上互斥的 flag 同时成立。
4. 某次毕业错误是否正是由 `schoolCalendarSyncedAt` 回退链触发，仍需用实际 prompt 和调用日志确认；但无论是否为本次直接触发点，该回退都不应继续作为学年真值来源。
5. 毕业正文生成时，主要角色列表/场景氛围对模型的影响可能强于普通 school identity 提示，导致“同场角色”被扩写成“共同毕业”。
6. 若某个目标没有进入本轮 `targets`，其学校身份提示可能根本没有进入正文上下文；需要从实际生成日志确认。

不得在没有捕获具体 prompt、模型响应、解析结果和提交 delta 前，把以上推测写成确定根因。

## 9. Aldent 审查约束

本轮用户已经给出明确人工失败结论，所以旧的自动测试通过记录不能覆盖该结论。

下一窗口完成任一 loop 后必须再次提供：

- 可复现的正例与反例输入。
- Chrome 页面实际结果。
- 路线变量/学校身份的最终状态证据。
- 必要的 prompt、模型输出、提交日志或宿主楼层证据。
- 新的人工审查邀请。

没有新的人工验收，不得宣称“已可作为正式流程使用”。
